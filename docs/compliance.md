## 1. NIST IR 8547 — transition to post-quantum cryptography

IR 8547 sets the timeline for retiring *quantum-vulnerable* public-key algorithms (RSA, ECDSA,
EdDSA, finite-field and elliptic-curve Diffie-Hellman): **deprecated after 2030** for the
112-bit-security parameter sets, **disallowed after 2035** for all of them. Symmetric primitives with
≥ 128-bit security (AES-128/192/256, SHA-2/SHA-3) are not affected by the quantum timeline.

| Algorithm in PQ-Chat | Where (CBOM ref) | Quantum-vulnerable? | IR 8547 status (draft) | PQ-Chat position |
|---|---|---|---|---|
| ML-KEM-768 (FIPS 203) | handshake, ratchet (`alg-mlkem768`) | No | Approved, the target | ✅ Core of key establishment |
| ML-DSA-65 (FIPS 204) | identity + prekey signatures (`alg-mldsa65`) | No | Approved, the target | ✅ Required on every prekey |
| X25519 | handshake, DH ratchet (`alg-x25519`) | **Yes** | Disallowed after 2035 | ◐ Only ever *combined* with ML-KEM (hybrid); security does not rest on it. Removable by switching to `pq-only` key establishment |
| Ed25519 | identity signatures (`alg-ed25519`) | **Yes** | Disallowed after 2035 | ◐ Always paired with ML-DSA-65 (both must verify). Initiator authentication still rests on X25519 (pentest F-02) — the one classical dependency to remove before 2035 |
| ECDSA P-256 | demo TLS certificate (`alg-ecdsa-p256`) | **Yes** | Disallowed after 2035 | ◐ Transport authentication only; replace with an ML-DSA or composite certificate when browsers/OpenSSL and CAs support it |
| X25519MLKEM768 | TLS 1.3 key exchange (`alg-x25519mlkem768`) | No (hybrid) | Hybrid allowed during the transition | ✅ Negotiated by default (M7 capture) |
| AES-256-GCM, HKDF/HMAC-SHA-256, SHA-256 | everywhere | No | Approved | ✅ 256-bit keys keep ≈ 128-bit security against Grover |
| Argon2id | key store (`alg-argon2id`) | n/a (symmetric) | Not a NIST-approved KDF (verify: NIST approves PBKDF2, SP 800-132) | ◐ Chosen for memory-hardness; in a FIPS-only environment it would need replacing by PBKDF2 or wrapping |

**Transition plan derived from the table**

| By | Action |
|---|---|
| now | Hybrid by default (done); `classical` mode refused unless explicitly allowed (SR-6) |
| 2028 | Add ML-DSA transcript signature by the initiator as an option (fixes F-02; deniability trade-off) |
| 2030 | Remove `classical` mode entirely; TLS certificate moves to ML-DSA/composite when available |
| 2035 | Drop X25519 and Ed25519 from new sessions (`pq-only` becomes the default) unless IR 8547 final allows hybrids beyond 2035 |

Note also: none of the libraries used is a FIPS 140-3 validated module (CBOM `certificationLevel`
= none). This is acceptable for a research prototype and is a deployment gap, not a design gap.

## 3. Data minimisation and data protection

Principles from the GDPR (Art. 5(1)(c) data minimisation, Art. 5(1)(e) storage limitation, Art. 25
data protection by design and by default, Art. 32 security of processing) applied to the relay, the
only component run by a third party:

| Data at the relay | Needed for | Minimisation applied | Retention |
|---|---|---|---|
| Username | addressing | chosen by the user; no e-mail, phone number or real name required | until account deletion |
| Public identity keys and signatures | key distribution | public by design | until account deletion |
| Signed and one-time prekeys (public) | asynchronous session start | one-time keys deleted when handed out (SR-10) | ≤ 30 / 90 days (expiry, SR-18) |
| Queued ciphertext, sender, recipient, time | store-and-forward | content end-to-end encrypted and padded; no read receipts, no profile, no contact list | deleted on delivery, max 30 days (SR-20), `secure_delete` |
| IP addresses, logs | operation | relay logs no usernames, IPs or message metadata (SR-25) | not stored by the application |

**Data protection by design (Art. 25):** the strongest measure is architectural — the relay never
receives content or private keys (confirmed forensically, M9), so a relay breach exposes metadata
only. **Breach handling (Art. 33/34, verify applicability):** a relay compromise exposes
who-talks-to-whom for queued messages and the account list; the IR playbook (`docs/forensics.md` §5)
includes assessing whether this triggers notification duties.

**Residual privacy gap:** social-graph metadata at the relay (threat T-15, pentest F-10). Sealed
sender, private contact discovery and mixnets are future work.
